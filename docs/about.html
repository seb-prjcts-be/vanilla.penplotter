About vanilla.penplotter

A pen plotter is the slowest printer you can own, and the only one that draws. I built this engine because I wanted a drawing written in JavaScript to reach that pen without a detour through files and other people's software.

Why

The usual road from a generative sketch to paper has four stops: capture the sketch as an SVG, clean and sort it in vpype, open it in Inkscape, send it with the plotter's own extension. Each stop works. Together they turn a five-second idea into a ten-minute ritual, and every stop forgets what the sketch knew: which lines belong together, which pen they want, in which order they should be drawn.

vanilla.penplotter keeps that knowledge. A sketch builds geometry in millimetres, the engine removes wasted travel, orders the paths, estimates the time, and either writes the file you still need or, on a tested machine, streams the plan straight to the motors. The road becomes one line: plot.go() in the p5 adapter, driver.run(plot.plan()) here.

Where it stops

  • Not a drawing library. It has primitives, fills and an SVG importer, but no curves, no text, no booleans. Draw with p5.js, p5.gysin, Paper.js or plain arrays; hand the points over.
  • Not p5.plotSvg. p5.plotSvg captures a p5 sketch as an SVG and covers far more of p5's drawing API. It deliberately stops there. This engine starts there: it reads that SVG, plans it and plots it.
  • Not vpype. vpype is the mature reference for line sorting, merging and simplification, in Python, on the command line. The optimizer here is the browser-sized version of the same ideas.
  • Not a universal driver. One machine profile has been plotted with. Everything else exports SVG, HPGL or G-code and stays honest about it.

The machine

Development and every physical test happen on one plotter: an iDraw HSE with an A2 bed, an EBB board and firmware 3.0.2. It is a CoreXY machine, like an AxiDraw: motor one moves X + Y, motor two moves X − Y, 80 steps per millimetre at 16× microstepping, a travel of 594 × 432 mm. The board has no homing, so the position of the carriage when the plot starts is the origin. Those facts were measured on paper on 2026-09-21, not copied from a datasheet, and they live in the header of src/driver/ebb.js.

The driver plans motion the way the machine likes it: every stroke ramps up from rest, cruises at the plan's speed, slows into corners by how sharp they are and ramps down again, sent as exact-step low-level moves with the board's motion queue kept full. Around that, the safety net is unchanged: a bounds check before the first byte, one acknowledgement per command, and a single safe stop for abort and error alike: motion halted, pen up, motors off. Pause and resume are on the roadmap, not in the code.

Two libraries, one direction

If you draw in p5.js you want the other one. The engine knows nothing about p5.js. p5.penplotter is the adapter: three methods on the p5 prototype, no planning or machine code of its own, and a version check that refuses an engine too old for the driver it is handed. The dependency runs one way, and the Requirements table is identical in both READMEs because a test says it has to be.

How this was made

Designed and directed by Sebastien Vanblaere, written with AI assistance in long working sessions, and held to a simple rule: nothing is claimed that a test or a plot on paper has not shown. The commit history is in his name only. The architecture document is larger than the code on purpose; it is the target, and the roadmap says which part of it exists.

Related work

  • p5.plotSvg: SVG capture for p5.js, by Golan Levin.
  • p5.plotterControl: live control of GRBL pen plotters from p5.js.
  • vpype: the Swiss army knife for plotter vector graphics.
  • AxiDraw Python API: the reference for reliable EBB motion.
  • p5.gysin and p5.waves: the sister libraries; the first exports plotter-safe SVG this engine can read, the second supplies the numbers the examples draw with.
